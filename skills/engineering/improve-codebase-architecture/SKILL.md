# Improve Codebase Architecture

审计代码仓库在两个维度上的健康度：**目录组织**（代码是否按清晰的结构整理好）与**文件内部设计**（每个文件的设计是否优雅）。目标是**可测试性**和**AI 可导航性**。把发现项汇总成 HTML 报告，再就你选中的项与用户深入讨论。

本命令使用 `/codebase-design` skill 的架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口即测试面"、"一个适配器 = 假想接缝，两个 = 真接缝"）。每条建议都用这些精确术语——不要漂移到"组件""服务""API"或"边界"。

检查的标准有两类：本项目 `AGENTS.md`（及 `CLAUDE.md`、`CONTEXT.md`）声明的约定与编码准则，以及通用的工程最佳实践。项目声明了的，以项目约定为准；项目没声明的，用通用最佳实践判断。

发现项的领域名词用 `CONTEXT.md` 的词汇；与 ADR 冲突的发现项，只有摩擦真实到值得重开时才摆出来，并清楚标注。不要列出所有理论上的违规。

## 流程

### 1. 探索

**先定范围再扫描——YAGNI。** 深化模块的收益是让未来的改动更容易，所以优先看近期频繁改动的部分。确定*看哪里*再开始看：

- 用户指了方向——某个模块、某个子系统、某个痛点——直接用，跳过下面的推断。
- 否则，回溯 commit 历史（`git log --oneline --since="3 months ago" --stat`）找热区——反复出现在提交里的文件和目录，让它们牵引你的注意力。如果改动分散没有明显热区，再扩大范围。

先读项目的约定来源：

- `AGENTS.md`、`CLAUDE.md`：项目声明的目录结构，以及编码准则（尤其“编码准则”一节）。
- `CONTEXT.md`、`docs/adr/`：领域语言与已定的架构决策。检查时不要重新争议 ADR；与 ADR 冲突的发现项，只有摩擦真实到值得重开时才摆出来，并清楚标注。

然后派两个子代理并行走查两个维度——一个走查"目录组织"、一个走查"文件内部设计"，带着下面两组透镜，记下违反以下检查点的地方。

具体怎么派子代理因 harness 而异，见末尾"多 harness 适配"。

#### 透镜一：目录组织

代码是否按清晰的结构整理好了。留心：

- **上帝目录**：单个目录下文件职责跨越多个不相关领域。
- **依赖泄漏**：高层模块直接 import 底层实现细节（如 utils、internal）；依赖出现循环；跨层访问本该隔离的实现。
- **Co-location**：一个模块的实现、测试、类型是放在一起，还是被拆散到按技术类型分的目录（所有 controller 一堆、所有 model 一堆）？理解一个概念要在多个目录间来回跳，就是信号。
- **命名一致**：目录和文件的命名约定（大小写、单复数、风格）是否前后一致？
- **碎片与膨胀**：有没有大量做同一件事的平行目录，或者过度细分、每个目录只剩一两个文件的碎目录？
- **孤儿与死目录**：有没有空目录、放在奇怪位置的单文件、没人引用的遗留目录？

然后对照 `AGENTS.md` / `CLAUDE.md` 声明的结构：声明的组织实际是否如此？声明的分层是否被遵守？

#### 透镜二：文件内部设计

每个文件的设计是否优雅。参照 `AGENTS.md` 的”编码准则”一节，留心：

- **浅模块**：接口参数或返回值几乎暴露全部实现；接口泄露实现细节，逼调用方懂内部。
- **过度拆分**：多个薄包装函数只是转发调用，删除后不会集中复杂度。用**删除测试**判断：删除该层后，复杂度是集中了（说明它有杠杆），还是只是搬走了（说明是透传层）？
- **过度工程**：只有一个实现的接口、只有一个子类的抽象基类；投机的错误处理（为不会发生的错误包 try/catch、对永不为 null 的值加检查）；没必要的可配置性（batch size、重试次数做成参数）。
- **职责聚焦**：一个文件是在讲一个概念，还是上帝文件什么都往里塞？
- **风格一致**：文件内部、以及它与项目其余部分的风格（引号、命名、缩进、注释密度）是否统一？有没有外来风格混入？
- **可测试性**：核心逻辑能否通过当前接口测到？有没有”逻辑跟 I/O、框架耦合，没法独立测”的信号？代码库哪些部分没测试，或通过当前接口难以测试？纯函数是否仅为可测试性提取，但真正的 bug 藏在调用方式里（缺少**局部性**）？
- **依赖**：有没有引入项目已有东西本可替代的依赖（有 fetch 还加 axios，有原生方法还加 lodash）？
- **概念与命名**：变量、函数、类型的名字是否抓住了本质？相邻概念有没有划清界限、不混用不模糊？
- **死代码与陈旧注释**：注释描述的还在不在？有没有没人调用的死代码？

探索完成的标志：两个子代理都返回结果，每个发现项都包含具体文件路径或目录路径、问题描述、改进建议。

### 2. 以 HTML 报告呈现发现项

把一份自包含的 HTML 文件写到系统临时目录，不要落进仓库。临时目录从 `$TMPDIR` 解析，回退到 `/tmp`（Windows 用 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，每次运行一个新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告知绝对路径。

报告用 **Tailwind（CDN）** 做布局与样式，用 **Mermaid（CDN）** 画图。每个发现项都配一张**前后对比可视化**。要直观。

报告分两大类章节：**目录组织**（`#directory`）与**文件内部设计**（`#file-design`）。每项一张卡片：位置、问题、建议、前后对比图，外加两项：**依据**（触了哪个透镜或 `AGENTS.md` 的哪条准则，标注是”项目约定”还是”通用最佳实践”）与**推荐程度**（`Strong` / `Worth exploring` / `Speculative`，以徽章呈现）。末尾放一个**首推方案**章节：先动哪个发现项，为什么。

卡片完整字段、HTML 脚手架、图表模式、样式指引与措辞规矩见 [references/html-report.md](references/html-report.md)。

此时**不要**动手改代码。文件写好后，问用户：”想对哪个发现项采取行动？或需要我详细解释哪一项？”

### 3. 深入讨论

用户选定发现项后，调用 `/grilling` skill 与用户走决策树——约束、依赖、深化后模块的形状、接缝背后放什么、哪些测试能保留。

讨论过程中，随着决策落地，同步运行 `/domain-modeling` skill 维护领域模型：

- **深化后的模块用了 `CONTEXT.md` 里没有的概念？** 把术语加到 `CONTEXT.md`。文件不存在时懒创建。
- **对话中锐化了模糊术语？** 当场更新 `CONTEXT.md`。
- **用户以有力理由拒绝了候选？** 提议写 ADR：「要我记一条 ADR，免得以后的架构审计再提同样的建议？」只在理由对未来探索者有参考价值时提议——跳过临时性理由（”现在不值得做”）和不言自明的理由。
- **想探索深化模块的备选接口？** 用 `/codebase-design` 的 design-it-twice 并行子代理模式。

## 多 harness 适配

第 1 步的抽象行为（并行走查两个维度、汇总后写报告）在所有 harness 都一样。**具体怎么派子代理**因 harness 而异，按当前运行的 harness 读对应文件：

- [Claude Code（含 ultracode 模式）](references/harness-claude-code.md)
- [Kimi Code](references/harness-kimi-code.md)
- [mimo code](references/harness-mimo-code.md)
- [zcode](references/harness-zcode.md)

第 2 步写 HTML 报告、第 3 步调 `/to-issues` 的工具用法不依赖特定子代理类型，按上面 SKILL.md 走即可。

## 下一步

完成报告后，根据用户选择：

- 报告里挑出一项讨论完，准备动手：落代码用 `/implement`
- 讨论中记录了多个待办：拆成 issue 用 `/to-issues`
