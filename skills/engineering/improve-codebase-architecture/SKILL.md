# 改进代码库架构

把架构摩擦暴露出来，提出**深化机会**——把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

本命令_参考_项目的领域模型，并建立在共享的设计词汇之上：

- 跑 `/codebase-design` skill 获取架构词汇（**模块**（module）、**接口**（interface）、**深度**（depth）、**接缝**（seam）、**适配器**（adapter）、**杠杆**（leverage）、**局部性**（locality））及其原则（删除测试、"接口即测试面"、"一个适配器 = 假想接缝，两个 = 真接缝"）。每条建议都精确使用这些术语——不要漂移到"组件""服务""API"或"边界"。
- `CONTEXT.md` 里的领域语言为好接缝命名；`docs/adr/` 里的 ADR 记录了本命令不应重新争议的决策。

## 流程

### 1. 探索

**先定范围再扫描——YAGNI。** 深化模块的收益是让它未来的改动更容易，所以多关注近期变动过的代码。看之前先确定*看哪里*：

- 用户指了方向——某个模块、某个子系统、某个痛点——直接用，跳过下面的推断。
- 否则，回溯一段足够长的 commit 历史（`git log --oneline`）找热区——反复出现的文件和区域——让那些路径先牵引你的注意力。如果改动分散、没有明显热区，扩大范围。

先读项目的领域词汇表（`CONTEXT.md`）和你要触碰区域的任何 ADR。

然后派一个子代理走查代码库。不要套死板的启发式规则——有机地探索，记下你感受到摩擦的地方：

- 理解一个概念需要在许多小模块之间来回跳，出现在哪里？
- 哪里的模块是**浅**的——接口几乎和实现一样复杂？
- 哪里的纯函数只是为可测试性而提取，但真正的 bug 藏在它们的调用方式里（没有**局部性**）？
- 紧耦合的模块在哪里跨过接缝泄漏？
- 代码库哪些部分没测试，或通过当前接口难以测试？

对任何你怀疑是浅的东西做**删除测试**：删掉它会集中复杂度，还是只是把它搬走？"集中了"就是你要的信号。

### 2. 以 HTML 报告呈现候选

把一份自包含的 HTML 文件写到系统临时目录，不要落进仓库。临时目录从 `$TMPDIR` 解析，回退到 `/tmp`（Windows 用 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，每次运行一个新文件。为用户打开它——Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`——并告知绝对路径。

报告用 **Tailwind（CDN）** 做布局与样式，用 **Mermaid（CDN）** 画图——当图/流/时序能可靠传达结构时。把 Mermaid 和手工打造的 CSS/SVG 可视化混着用——关系是图状的（调用图、依赖、时序）用 Mermaid，想要更有编辑感的（质量图、剖面图、折叠动画）用手工搭建的 div/SVG。每个候选都配一张**前后对比可视化**。要直观。

每个候选渲染一张卡片：

- **文件**——涉及哪些文件/模块
- **问题**——当前架构为什么会造成摩擦
- **方案**——用平实的语言描述会改什么
- **收益**——用局部性和杠杆解释，以及测试会怎么改善
- **前后对比图**——并排、手绘，展示浅和深的样子
- **推荐程度**——`Strong`、`Worth exploring`、`Speculative` 三档之一，以徽章呈现

报告末尾放一个**首推方案**章节：先动哪个候选，为什么。

**领域用 `CONTEXT.md` 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了"Order"，就说"Order 接单模块"——不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：候选与现有 ADR 矛盾时，只有摩擦真实到值得重开该 ADR 才摆出来。在卡片里清楚标注（例如一个警告标注：_"与 ADR-0007 矛盾——但值得重开，因为……"_）。不要列出 ADR 禁止的每一条理论上的重构。

完整 HTML 脚手架、图表模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

此时**不要**提出接口。文件写好后，问用户："想探索哪一个？"

### 3. Grilling 循环

用户选定候选后，跑 `/grilling` skill 与他们一起走决策树——约束、依赖、深化后模块的形状、接缝背后放什么、哪些测试能保留。

随着决策落地，副作用就地发生——跑 `/domain-modeling` skill 维护领域模型：

- **深化后的模块用了 `CONTEXT.md` 里没有的概念命名？** 把术语加进 `CONTEXT.md`。文件不存在就懒创建。
- **对话中锐化了某个模糊术语？** 当场更新 `CONTEXT.md`。
- **用户以有力理由拒绝了候选？** 提议写 ADR：「要我记一条 ADR，免得以后的架构审计再提同样的建议？」只在理由确实会被未来探索者需要、以免重复建议时提议——跳过临时性理由（"现在不值得做"）和不言自明的理由。
- **想探索深化模块的备选接口？** 跑 `/codebase-design` skill，用它的 design-it-twice 并行子代理模式。
