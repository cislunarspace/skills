# UI 原型

在同一路由下生成**几套截然不同的 UI 变体**，用浮在底部的切换条切换。用户在浏览器里来回翻，挑一个（或从每套里偷一点），其余扔掉。

如果问题是关于逻辑/状态而不是东西该长什么样——走错路了。用 [LOGIC.md](LOGIC.md)。

## 什么时候该用这个形状

- "这个页面该长什么样？"
- "我想在定下来之前先看几个 dashboard 方案。"
- "给设置屏试一个不同的布局。"
- 任何用户否则要在脑子里花一天在三个模糊草图之间挑的情况。

## 两种子形状——强烈偏好子形状 A

UI 原型在**贴着应用的其余部分**时好判断得多——真实的页头、真实的侧栏、真实的数据、真实的密度。一个孤立的一次性路由是个真空：每个变体单独看都还行。只要有合理的现有页面能承载变体，默认选子形状 A。只在原型确实没有附近的家时才用子形状 B。

### 子形状 A —— 在现有页面上做调整（首选）

路由已经存在。变体渲染在**同一路由**上，由一个 `?variant=` URL 查询参数控制。已有的数据获取、参数和鉴权都保留——只换渲染。这是默认；没有具体理由不选它就用它。

如果原型是为一个还没有页面但*天然会住在某个页面里*的东西（dashboard 的新区块、设置屏上的新卡片、现有流程里的新一步）——那仍然是子形状 A。把变体挂在宿主页面里。

### 子形状 B —— 一个新页面（最后手段）

只在被原型化的东西确实没有现有页面可住时用——例如一个全新的顶层界面，或一个没法合理嵌入任何地方的流程。

按项目已有的路由约定建一个**一次性路由**——别另起一套顶层结构。命名上让人一眼看出是原型（例如路径或文件名里带 `prototype` 字样）。同样的 `?variant=` 模式。

定下子形状 B 之前，先做个 sanity check：真的没有现有页面能嵌入吗？一个空路由会藏住有内容时本会暴露的设计问题。

两种子形状的浮动切换条是一样的。

## 流程

### 1. 把问题说出来，挑 N

默认 **3 个变体**。超过 5 个就不再截然不同，开始变噪音——封顶 5。

在原型的位置或文件顶部的注释里，用一行写下计划：

> "设置页的三个变体，用 `?variant=` 切换，在现有 `/settings` 路由上。"

不管用户是否在场反驳，这都管用。

### 2. 生成截然不同的变体

起草每个变体。每个都要服从：

- 页面的目的和它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便哪个）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同的布局、不同的信息层次、不同的主要 affordance，不只是不同颜色。三个微调过的卡片网格不是 UI 原型，是壁纸。两个草稿出来太像，就带着明确的"不要用卡片网格"指示重做一个。

### 3. 把它们接到一起

在路由上建一个切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形状 A（现有页面）：把所有现有数据获取放在切换器之上；每个变体只改渲染的子树。

子形状 B（新页面）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 搭浮动切换器

屏幕底部居中一个小的固定位置条，三个部分：

- **左箭头** ——循环到上一个变体（回绕）。
- **变体标签** ——显示当前变体 key，如果变体导出了名字也显示那个名字。例如 `B — Sidebar layout`。
- **右箭头** ——循环到下一个（回绕）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由——Next 上 `router.replace`、React Router 上 `navigate` 等），让变体可分享、刷新稳定。
- 键盘：`←` 和 `→` 箭头键也循环。`<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截箭头键。
- 视觉上与页面区分开（例如高对比药丸状、微妙的阴影），让它显然不是被评估的设计的一部分。
- 生产构建里隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查作门，免得一个走漏的原型把切换条发到用户那里。

把切换器放进一个共享组件，两种子形状都能复用。放在项目里放共享 UI 的地方。

### 5. 交接

给出 URL（和 `?variant=` key）。用户会在方便时翻看。有意思的反馈通常是**"我想要 B 的页头搭 C 的侧栏"**——那才是他们真正想要的设计。

### 6. 记下答案并清理

一旦某个变体赢了，记下答案——哪个变体、为什么——然后按 [SKILL](SKILL.md) 描述的方式留存原型。把赢家折回真实代码，其余移到一次性分支上，不进 main：

- **子形状 A** ——把赢家折回现有页面；从 main 删掉落选变体和切换器。
- **子形状 B** ——把赢家升为真实路由；从 main 删掉一次性路由和切换器。

完整的变体集是一手资料，所以它上一次性分支，不上垃圾桶——留在 main 的变体组件和切换器很快腐烂、困惑下一个读者。

## 反模式

- **只差颜色或文案的变体。** 那是微调，不是原型。真正的变体在结构上意见不合。
- **变体间共享太多代码。** 共享一个 `<Header>` 可以；共享一个 `<Layout>` 就毁了意义。每个变体应能自由地丢掉布局。
- **把变体接到真实 mutation。** 只读原型没问题。变体需要 mutate，就指向一个打桩——问题是"这东西该长什么样"，不是"后端能不能用"。
- **把原型直接提上生产。** 变体代码是在原型约束下写的（没测试、错误处理最小）。折进去时正经重写。
