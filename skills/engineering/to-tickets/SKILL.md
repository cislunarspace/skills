# To Tickets

把计划、规格或对话拆成一组**工单**——曳光弹（tracer bullet）式的垂直切片，每张声明**阻塞**它的那些工单。

issue tracker 和分诊标签词汇应当已提供——如未提供，跑 `/setup-ouyangjiahong-skills`。

## 流程

### 1. 收集上下文

基于对话上下文里已有的内容工作。若用户传入了引用（规格路径、issue 编号或 URL）作为参数，抓取它，读完整正文和评论。

### 2. 探索代码库（可选）

若你还没探索过代码库，先探索以了解代码的当前状态。工单标题和描述应使用项目的领域术语表词汇，遵守你将要改动区域的 ADR。

寻找前置重构（prefactor）代码以让实现更轻松的机会。"先把改动变容易，再做容易的改动。"

### 3. 起草垂直切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片切一条窄但完整的路径，穿过每一层（schema、API、UI、测试）——是垂直切片，不是某一层的水平切片
- 完成的切片可独立演示或验证
- 每个切片的大小控制在一次全新的上下文窗口能装下
- 任何前置重构应先做

</vertical-slice-rules>

给每张工单标上**阻塞边**——必须先完成才能开始的其他工单。没有阻塞的工单可以立即开始。

**宽重构是垂直切片的例外。** **宽重构**是单一机械改动——重命名一列、改一个共享符号的类型——其影响半径扇形扩散到整个代码库，单次编辑就破坏数千个调用点，没有垂直切片能保持绿灯。不要硬塞进曳光弹；把它排成**扩展–收缩**。先扩展：在旧形式旁边加上新形式，什么也不破坏。然后按影响半径分批迁移调用点（按包、按目录），每批是独立的工单，被扩展工单阻塞，因为旧形式仍存在，CI 逐批保持绿灯。最后收缩：一旦没有调用方剩余，删除旧形式，这张工单被每个迁移批次阻塞。当连批次都无法独自保持绿灯时，保持顺序，但让它们共享一个集成分支，所有批次阻塞一张最终的集成验证工单——绿灯只在那里承诺。

### 4. 向用户确认

把拟定的拆分呈现为编号列表。每张工单展示：

- **标题**：简短的描述性名称
- **被谁阻塞**：哪些其他工单（如有）必须先完成
- **交付什么**：这张工单使之跑通的端到端行为

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对不对——每张工单是否只依赖真正卡住它的工单？
- 有没有该合并或进一步拆分的？

迭代直到用户批准拆分。

### 5. 把工单发布到已配置的 tracker

发布批准的工单。**怎么发**取决于 `/setup-ouyangjiahong-skills` 配置的 tracker——工单本身两种方式都一样，只有阻塞边的形状变了：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单写一个文件，按依赖顺序（阻塞者优先）从 `01` 编号。每个文件的"Blocked by"列出它依赖的编号/标题。用下面的单工单文件模板——一文件一工单，绝不合并成一个文件。
- **真实 issue tracker（GitHub、Linear、…）** → 按依赖顺序（阻塞者优先）每张工单发一个 issue，这样每张工单的阻塞边能引用真实标识符。平台有原生阻塞/子 issue 关系就用它；否则把每张工单的"Blocked by"设为阻塞 issue。除非另有指示，套上 `ready-for-agent` 分诊标签——这些工单天生就是 agent 可认领的。

做**前沿**：任何阻塞都已完成的工单。对纯线性链条，就是从上到下。

不要关闭或修改任何父 issue。
