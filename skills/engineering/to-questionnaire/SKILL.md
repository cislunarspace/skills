# To Questionnaire

把用户独自答不了的东西变成一份**问卷**——一份 Markdown 文档，交给一个人异步填写，或在会议中一起填写。对方拥有用户缺乏的知识；问卷把那些知识抽出来。

**追问发送端，不是追问主题。** 只采访用户能回答的事：发给谁、需要拿回什么。问卷里的问题则瞄准对方知道而用户不知道的**缺口**。

## 流程

### 1. 发给谁？

一个回合问清对方的角色、专业程度、和用户的关系。这决定了问卷的语气和需要携带多少上下文。完成标志：知道对方是谁、对方知道什么用户不知道的。

### 2. 需要拿回什么？

一个回合问清用户独自解决不了的具体决策或事实。完成标志：有一个具体清单——用户拿到回答后能做什么或决定什么。

### 3. 写问卷

针对步骤 1-2 的缺口起草问题。按下面的模板写，存为当前目录下的 `to-questionnaire-<slug>.md`（slug 取主题），报告路径。完成标志：文件存在，步骤 2 的每条都有对应问题覆盖。

## 文档结构

把文档定位为**发现式问卷**：用户缺上下文，对方有。最重要的问题排最前——异步意味着你可能只有一次机会。问题超过一打时，按主题用 `##` 分组。

```markdown
# <问卷标题>

**目的：** 为什么做这份问卷、什么决策取决于回答。

**来自：** <用户> — **给：** <对方> — **你的回答会怎么用：** <去向>

## 背景

一段话，给不在用户脑中的对方定位。够回答好就行，不是一页纸。

## 怎么回答

截止日期和大致工作量。部分回答和"不知道"也有用——不确定的标出来，别跳过。

## <主题标题>

### <问题？>

_为什么问这个：这句话解释了这个问题为什么重要，防止被敷衍回答。_

> （回答空间）

## 还有什么？

收尾的兜底：有什么我们没问但应该知道的？
```

## 边界情况

| 情况 | 处理方式 |
|------|----------|
| 用户不知道发给谁 | 先帮用户理清需要什么知识，再推断合适的对象 |
| 用户需要问多人 | 每人一份问卷，不要混在一起 |
| 问题有歧义 | 写出问题后让用户检查一遍再发 |

## Checkpoint

问卷写完后展示给用户确认，确认后再让用户发送。

## 下一步

- 问卷发出去后：等回答，回答到了继续用当前 skill 的知识更新方案
- 回答涉及新的技术决策：跑 `/grilling` 或 `/batch-grill-me`
