# 深化

给定依赖后，如何安全地深化一个由浅模块组成的簇。假定你已熟悉 [SKILL.md](SKILL.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个深化候选时，把它的依赖分类。类别决定了深化后的模块如何跨接缝被测试。

### 1. 进程内

纯计算、内存状态、无 I/O。总是可深化——合并这些模块，直接通过新接口测试。不需要适配器。

### 2. 本地可替代

有本地测试替身的依赖（用 PGLite 替 Postgres、内存文件系统）。替身存在就可深化。深化后的模块让替身跑在测试套件里来测。接缝是内部的；模块的外部接口处没有端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的你自己的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

建议的话形如：*"在接缝处定义一个端口，生产实现一个 HTTP 适配器、测试实现一个内存适配器，这样即便跨网络部署，逻辑也落在一个深模块里。"*

### 4. 真正的外部（Mock）

你不掌控的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖当作注入的端口接收；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器意味着一个假想的接缝；两个适配器才意味着真的接缝。** 除非至少能证明两个适配器（通常是生产 + 测试）合理，否则不要引入端口。单适配器的接缝只是间接层。
- **内部接缝 vs 外部接缝。** 一个深模块可以有内部接缝（对其实现私有、给它自己的测试用），也可以有位于其接口处的外部接缝。不要仅仅因为测试用了某个内部接缝，就把它通过接口暴露出去。

## 测试策略：替换，不要叠加

- 浅模块上的旧单元测试，一旦深化后模块的接口处有了测试，就变成了废物——删掉。
- 在深化后模块的接口处写新测试。**接口就是测试面**。
- 测试断言的是通过接口能观察到的结果，不是内部状态。
- 测试应当扛住内部重构——它们描述的是行为，不是实现。如果一个测试在实现变了之后也得跟着改，它就测到接口背后去了。
